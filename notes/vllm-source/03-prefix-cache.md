# 源码笔记 3 · 前缀缓存：怎么命中、怎么被挤掉

对应 vLLM v0.30.0。代码位置写成 `vllm/<路径>:<行号>`。

## 要解决的问题

1. 为什么 Agent 负载里「所有会话共用系统提示词」时命中率 86%，「每个会话各用一套」时连会话内部的逐轮复用都是 0%（`results/agent/summary.md`）？
2. 第一周 `bench.sh` 没传 seed 时，随机负载为什么会命中 4%~10%（`results/bench/knee.md`）？
3. 共享前缀实验（512 token 前缀 + 512 token 随机）的命中率为什么是 49.8%？

## 关键数据结构

| 名字 | 位置 | 作用 |
| --- | --- | --- |
| 块哈希 `hash_block_tokens` | `vllm/v1/core/kv_cache_utils.py:638` | 一个满块的哈希 = hash(**前一块的哈希**, 本块 16 个 token, 额外键) |
| `cached_block_hash_to_block` | `vllm/v1/core/block_pool.py:146-147` | 哈希 → 块，查有没有算过 |
| `FreeKVCacheBlockQueue` | `kv_cache_utils.py:246-261` | 空闲块按 LRU 排；**带着哈希的空闲块仍然可以被命中**，直到被复用 |

哈希里带着前一块的哈希，所以一个块能命中，**前面所有块都必须一模一样**：这就是「前缀」的意思。
只有填满 16 个 token 的块才有哈希，最后一个不满的块永远不会被命中。

## 调用路径

1. **查**：新请求进来，`KVCacheManager.get_computed_blocks`（`vllm/v1/core/kv_cache_manager.py:265`）按块哈希从头往后找最长的命中前缀
   （`find_longest_cache_hit`，`kv_cache_manager.py:297`）。最多命中到 prompt 长度减 1，因为最后一个 token 必须真算一次才能拿到 logits（`kv_cache_manager.py:290-295`）。
2. **用**：命中的块引用计数加一，从空闲队列里摘出来（`touch`，`block_pool.py:749`），这部分 token 不用再算。
3. **还**：请求结束或被抢占，块归还到空闲队列（`free_blocks`，`block_pool.py:770`）。块里的数据和哈希都还在，下一个相同前缀的请求仍能命中。
   一个请求的块倒序归还，链尾的块排在队头，先被淘汰（`kv_cache_utils.py:256-261`）。
4. **挤掉**：别的请求要新块时，从空闲队列队头取（`get_new_blocks`，`block_pool.py:664`），取到的块如果带着哈希，就把这条缓存删掉（`_maybe_evict_cached_block`，`block_pool.py:726`）。
   **空闲块就是缓存**：缓存能活多久，取决于有多少别的请求在要新块。

## 对应本项目的哪个现象

**共享系统提示词时命中率高**：4,000 token 的系统提示词是 250 个块，所有会话的哈希链完全一样。只要有一个会话在用它，这些块的引用计数就不为 0，不会被挤掉；
就算短暂空闲，也会马上被下一个会话 `touch` 回来。所以 8 个会话时命中率 86.1%，并发越高、别的块越抢空间，命中率越低（16、32 个会话时 68.4%、65.3%）。

**各用各的系统提示词时，连会话内部的复用也失效**：一个会话的第 k 轮结束，它的块回到空闲队列。在它第 k+1 轮到来之前，另外 7 个会话正在用掉大量新块。
8 个会话同时进行需要约 3.6~6.2 万 token，KV 只有约 3 万 token，空闲队列很快被取空，这个会话的块被别人复用、哈希被删掉。等它的下一轮到了，只能从头算，所以命中率是 0%。
**缓存能不能活到下一轮，看的是 KV 容量够不够，而不是开没开前缀缓存。** 同样条件下 SGLang 在 8 个会话时还有 12.8%，基数树在紧张时多保住了一点；本笔记没有读 SGLang 的代码，不展开。

**第一周没传 seed 时的意外命中**：同样的「随机」提示词，块哈希也完全一样。上一档并发跑完的块还留在空闲队列里，下一档的同一批提示词就命中了。
KV 越大，空闲块被复用得越慢，留得越久：显存 0.90（18.6 万 token）和 AWQ（10 万 token）两组命中 4.4%、9.7%，KV 只有 1.3 万 token 的那组是 0%。

**512 token 共享前缀时命中率 49.8%**：每个请求 1,024 个输入 token，前 512 个（32 个块）所有请求都一样，后 512 个随机。
命中率按 token 算，理论上限正好 50%；实测 49.8%，差的那一点是最开始还没有缓存时的那几个请求。
