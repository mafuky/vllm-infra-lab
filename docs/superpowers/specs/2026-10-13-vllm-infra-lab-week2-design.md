## 1. 目的

### 1.1 为什么要有第二周

AI Infra 岗位的能力要求大致分三层：推理引擎（vLLM、SGLang）的优化实践、K8s 上的 GPU 调度与资源管理、Agent 平台与 LLM 网关。作者的第三层已有生产经历，第二层由第一周补上，最缺的是第一层的「优化实践」，以及 Infra 面试必问的弹性扩缩容和冷启动。第二周专门补这两块，并尽量和作者的 Agent 背景连起来。

### 1.2 本周回答的问题

| 问题 | 对应部分 | 产出 |
| --- | --- | --- |
| vLLM 和 SGLang 怎么选？ | 同模型、同客户端的对比压测 | 两个引擎在 5 档并发下的对比表 |
| Agent 场景下哪个更合适？ | Agent 式多轮负载压测 | 按轮次统计的首字延迟、前缀缓存命中率对比 |
| 新副本要多久才能接流量？怎么缩短？ | 冷启动分阶段计时和优化 | 冷启动时间线，以及至少两项优化的前后对比 |
| 流量上来时怎么自动扩容？ | KEDA 按排队请求数扩缩容 | 从触发扩容到新副本就绪的实测时间和看板截图 |
| 这些现象在源码里对应什么？ | vLLM 源码精读 | 三篇笔记，每篇对应一个实验中看到的现象 |

### 1.3 成功标准

全部满足才算完成：

1. vLLM 和 SGLang 用同一个压测客户端、同样的参数，在并发 1、4、16、32、64 下各跑一轮，产出对比表。表中注明两个引擎各自启动日志里的 KV Cache 容量，说明对比是否公平。
2. Agent 式负载在两个引擎上各跑「共享前缀」和「不共享前缀」两组，产出按轮次统计的 TTFT P50/P95 和前缀缓存命中率。
3. 冷启动时间线拆成调度、容器启动、加载权重、编译与 CUDA Graph 捕获、就绪五段，并完成至少两项优化的前后对比。
4. 压测流量上升时，KEDA 把 vLLM 从 1 个副本扩到 2 个；有 Grafana 截图显示排队数上升、副本增加、排队数回落，并记录从触发到新副本就绪的耗时。
5. 三篇源码笔记，每篇都引用本项目实验中的一个具体现象或数字。
6. README 新增第二周的结果章节，简历条目和面试问答同步更新。

## 4. 组件设计

### 4.1 SGLang 对比压测

**部署**

- 镜像使用 `lmsysorg/sglang:v0.5.20-cu130`（2026-09-18 发布），与 vLLM v0.30.0 同为 CUDA 13，驱动 580。KV 容量用其 `sglang:max_total_num_tokens` 指标与 vLLM 启动日志对齐。
- 模型同为 `/models/Qwen3-8B`（BF16），服务名同为 `qwen3-8b`，`--context-length 8192`，开启 `--enable-metrics` 供 Prometheus 采集。
- 显存参数的语义不同：vLLM 的 `--gpu-memory-utilization` 是总显存占比，SGLang 的 `--mem-fraction-static` 是权重加 KV 池的占比。不按参数值对齐，而是调整 SGLang 的参数，使两者启动日志里的 KV Cache 容量（token 数）接近，偏差控制在 10% 以内。这一点本身就是面试讨论点。
- `strategy: Recreate`，申请 1 张卡；运行 SGLang 时把 vllm 缩到 0，反之亦然。

**标准负载**

复用第一周的 `bench.sh` 和 `vllm bench serve` 客户端（`--backend openai`），参数完全一致：random 数据集，输入 1024、输出 256，`--ignore-eos`，5 档并发，每档不同 seed。vLLM 一侧直接复用 2026-10-15 用新 seed 重跑的 `baseline`，不再重跑；SGLang 一侧的 label 为 `sglang-baseline`。

### 4.2 Agent 式多轮负载

**为什么要单独测**

Agent 的请求和聊天不同：系统提示词加工具定义很长且所有会话共用，每轮把上一轮的工具结果追加进上下文，输入越来越长、输出很短。这种负载以 prefill 为主，前缀复用的效果决定首字延迟。vLLM 用基于哈希的自动前缀缓存，SGLang 用 RadixAttention（基数树），本实验看两者在这种负载下的实际差别。结果可能是任何一方占优，如实记录。

**负载模型**（脚本 `scripts/agent_workload.py`，在 bench-client Pod 内运行）

- 每个会话 6 轮。共享前缀 4,000 token（模拟系统提示词和工具定义），每轮新增 500 token（模拟工具返回或用户输入），每轮输出上限 150 token。第 6 轮上下文约 7,900 token，不超过 8,192 的上下文上限。
- 同时进行的会话数（并发）分 8、16、32 三档；每档总会话数为并发的 4 倍。
- 两组条件：
  - 共享前缀：所有会话用同一段 4,000 token 前缀。
  - 不共享前缀：每个会话的前缀各不相同，只保留会话内部的逐轮复用。两组之差就是跨会话共享前缀带来的收益。
- 文本由固定随机种子生成，用模型自带的分词器校准长度，两个引擎收到完全相同的请求序列。
- 走 `/v1/chat/completions`，关闭 Qwen3 思考模式。输出长度以响应里的 `usage` 为准。

**记录**

每个请求的轮次、TTFT（流式响应收到第一个 token 的时间）、总耗时、输入和输出 token 数。汇总成按轮次的 TTFT P50/P95，以及整体吞吐。前缀缓存命中率取引擎自身指标：vLLM 用 `vllm:prefix_cache_hits_total` 与 `vllm:prefix_cache_queries_total` 之比，SGLang 用其 cache hit rate 指标。第 1 天部署后核对 SGLang 的实际指标名。

### 4.3 冷启动计时与优化

**现成工具**（2026-10-13 探测）：vLLM v0.30.0 自带 `vllm bench startup`，能分别测冷启动和热启动（含编译缓存）；SGLang 暴露 `sglang:startup_time_seconds`、`sglang:weight_load_duration_seconds`、`sglang:startup_cuda_graph_time_seconds` 指标。`coldstart.py` 只补 K8s 调度和就绪两段，引擎内部各段用这两个现成来源交叉核对。

**分阶段计时**（脚本 `scripts/coldstart.py`）

删除 vllm Pod 让它重建，从以下来源取时间戳，拆成五段：

1. 调度：Pod 创建到被调度（K8s 事件）
2. 容器启动：调度到容器启动（K8s 事件；镜像已在本地，不含拉取）
3. 加载权重：vLLM 日志中权重开始加载到加载完成
4. 编译与 CUDA Graph 捕获：加载完成到引擎就绪的日志行
5. 就绪：引擎就绪到 readinessProbe 首次成功（Pod 的 Ready 条件时间）

每种条件重复 3 次取中位数。

**优化对比**

| 实验 | 做法 | 预期影响的阶段 |
| --- | --- | --- |
| 权重读取：冷盘 vs 页缓存 | 重建前执行 `echo 3 > /proc/sys/vm/drop_caches` 对比不清缓存 | 加载权重 |
| 持久化编译缓存 | 把 vLLM 的编译缓存目录挂到宿主机，对比首次和之后的启动 | 编译与 CUDA Graph 捕获 |
| 跳过 CUDA Graph | 加 `--enforce-eager`，对比启动时间，同时用 16 并发压测对比 ITL | 编译与 CUDA Graph 捕获（代价是推理变慢） |

第三项是取舍：启动快了，推理慢了。用数据说清楚什么场景值得这么做。

### 4.4 弹性扩缩容（双卡，一天）

**机制**

- 安装 KEDA v2.21.0（官方 YAML 清单）。选 KEDA 而不是 HPA 的原因：HPA 用自定义指标需要额外部署 prometheus-adapter，KEDA 直接查询 Prometheus，配置更少，还支持缩容到 0。
- ScaledObject 指向 `infer/vllm`，触发器为 Prometheus 查询 `avg_over_time(sum(vllm:num_requests_waiting)[1m:])`（第一周发现瞬时排队数在阈值附近来回跳），阈值 5（与第一周的排队告警一致），`minReplicaCount: 1`，`maxReplicaCount: 2`，缩容冷却 300 秒。
- 单节点、双卡，两个副本各占一张卡。K8s Service 按连接随机分发，不感知前缀缓存，讲解中说明这会降低缓存命中率，以及按前缀路由的方案如何解决。

**实验**

1. 稳态：并发 8，1 个副本。
2. 阶跃：并发升到 48 并保持 10 分钟。记录排队数越过阈值的时间、KEDA 修改副本数的时间、新 Pod 就绪的时间，以及期间的 TTFT P95。
3. 回落：并发降回 8，确认冷却期后缩回 1 个副本。
4. 与网关联动：阶跃期间经 LiteLLM 发请求，统计新副本就绪前有多少请求因超时转到百炼。这把第一周的降级和本周的扩容连成一个完整的应对链路：先降级兜底，再扩容恢复。

**可砍：缩容到 0**。副本为 0 时 vLLM 指标消失，KEDA 需要改用网关侧的请求指标触发，复杂度明显上升，时间不够就只在讲解中说明。

### 4.5 vLLM 源码精读

读第一周部署的同一版本（按镜像标签对应的 Git tag），笔记放在 `notes/vllm-source/`。每篇按「要解决的问题、关键数据结构、调用路径、对应本项目的哪个现象」四段来写：

1. **调度器与 continuous batching**：一个请求从进入等待队列到被调度、每一步怎么决定 prefill 和 decode 的配比。对应现象：第一周压测中排队数和 TTFT 随并发的变化；并回答 `knee.md` 待查问题 2（基线并发 32、64 时 ITL P95 75~79ms，而 `--max-num-seqs 32/64` 只有约 24ms）。
2. **KV Cache 显存块管理（PagedAttention）**：显存块池怎么分配、KV 满了以后怎么抢占。对应现象：启动日志中的 KV Cache 容量，以及 KVCacheNearFull 告警触发时的行为；并回答 `knee.md` 待查问题 1（`--max-num-seqs` 为什么会改变可用 KV 显存）。
3. **前缀缓存（可砍）**：块哈希怎么算、怎么命中、怎么淘汰，并简要对比 SGLang 的基数树。对应现象：4.2 节两组负载的命中率差异。

### 4.6 投机解码（可砍）

给 vLLM 开启 n-gram 投机解码（不需要草稿模型），对比两类输出：改写或摘要这类大量复用输入内容的任务，以及 random 数据集。看每 token 延迟在什么场景下下降、什么场景下反而变差。
